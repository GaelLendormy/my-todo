# Développement — M1

## Compatibilité vérifiée le 9 novembre 2026

Runtime local : Node 24.14.0 et pnpm 10.33.0. Nuxt 4.6.4 exige Node `^22.22.3 || ^24.15.0 || >=26.0.0` : il n'est donc pas retenu sur ce runtime. Nuxt **4.4.2** accepte `^20.19.0 || >=22.12.0` (métadonnées du paquet et [source officielle versionnée](https://github.com/nuxt/nuxt/blob/v4.4.2/packages/nuxt/package.json)). Vue **3.5.45**, TypeScript **5.9.3**, Drizzle **0.45.4** et better-sqlite3 **12.8.0** sont figés dans le manifeste et le lockfile.

Le [guide officiel Drizzle](https://orm.drizzle.team/docs/get-started-sqlite) prend en charge le pilote local better-sqlite3. Le [manifeste officiel du pilote 12.8.0](https://github.com/WiseLibs/better-sqlite3/blob/v12.8.0/package.json) prend en charge Node 24. L'installation utilise son binaire Linux précompilé lorsqu'il existe, sinon `node-gyp rebuild --release` nécessite Python, make et un compilateur C++. Le script natif du pilote est explicitement autorisé par `pnpm-workspace.yaml`. Node:sqlite n'est pas retenu : pas de changement de pilote nécessaire.

La page d'installation Nuxt a renvoyé un contenu Markdown non exploitable par le navigateur de recherche ; les prérequis ont été recoupés sur le manifeste officiel versionné et avec `pnpm view nuxt@4.4.2 engines`.

L'installation initiale a fait remonter des dépendances transitives récentes incompatibles entre elles. L'alignement utilise `@nuxt/eslint` 1.15.2, et des overrides pnpm pour `@nuxt/kit` 4.4.2, `@nuxt/cli` 3.34.0 et `@nuxt/devtools` 3.2.3. L'installation finale n'a plus signalé de conflit de peer dependencies. Le pilote s'est installé sans compilation de secours visible et a retourné SQLite **3.51.3** à l'ouverture d'une base en mémoire.

Les résultats d'installation et de validation seront consignés dans le [checkpoint](../runs/current.md). Les commandes d'utilisation sont dans le [README](../README.md).


## Organisation des tâches — M1

La migration [0001_categories.sql](../migrations/0001_categories.sql) ajoute les catégories et `tasks.category_id` nullable sans modifier la migration historique. Le journal Drizzle suit les migrations incrémentales. La connexion partagée dans [server/utils/database.ts](../server/utils/database.ts) ouvre SQLite avec `foreign_keys = ON` ; la référence `ON DELETE SET NULL` protège le déclassement atomique. Les règles de [catégories](../server/domain/categories.ts) utilisent la [normalisation partagée](../shared/category-names.ts), l’unicité étant arbitrée par SQLite, y compris entre connexions. Les champs d’un PATCH de tâche sont validés avant son unique écriture.

L’état des ressources et les mutations de catégories résident dans [useTaskResources.ts](../app/composables/useTaskResources.ts). Une lecture logique attend la fin des deux requêtes, y compris si l’une échoue ; leur publication est commune. Un échec ne remplace pas les données précédentes et ne lève pas l’incertitude. Le détail, le sélecteur et la navigation sont des composants séparés, sans stockage métier navigateur ni nouvelle dépendance. Le détail compare le brouillon à son état d’ouverture/confirmation pour envoyer seulement les champs modifiés, même après une relecture externe.

Les [tests SQLite](../tests/categories.test.ts) construisent aussi une base réellement au schéma 0000 avant montée. Les [parcours organisation](../tests/e2e/organization.spec.ts) couvrent les vues, le clavier, les pertes de réponses et la coordination ; les mocks historiques retournent désormais `categoryId`. Les scripts `check:persistence` et `check:recovery` vérifient aussi les catégories et associations sur des données jetables. Les contrats HTTP, gestes, migrations et reprises sont détaillés dans le [README](../README.md#organisation-m1--catégories). Les résultats exécutés et les validations tactiles rapportées par l’utilisateur sont consignés dans le [checkpoint](../runs/current.md). Les priorités, échéances et filtres sont ajoutés par M2, décrit ci-dessous.

## Étapes manuelles — M1

La [migration 0003](../migrations/0003_task_steps.sql) crée `task_steps` (FK cascade, titre valide, booléen, position entière positive ou nulle et unique par tâche). L’ordre est dense à partir de zéro. L’ajout utilise la fin de liste ; la suppression compacte les positions en deux phases positives dans une transaction pour respecter l’unicité. Aucune étape historique n’est créée. Le [schéma](../server/db/schema.ts) et les [types](../shared/types/task.ts) décrivent la même ressource. Réordonnancement/API d’ordre restent réservés à M2.

Les [opérations métier](../server/domain/task-steps.ts) et le refus `TASK_HAS_STEPS` acquièrent une transaction SQLite `immediate` avant toute lecture métier. Elles confirment ensemble parent et étapes, sans upsert tardif. Les lectures de liste chargent les étapes en lot dans une transaction cohérente, sans requête par parent. La suppression de dernière étape conserve la réalisation parent ; les autres mutations recalculent la réalisation depuis les étapes restantes. Les modifications SQL manuelles ne sont pas une interface métier supportée.

Le [contrat API et les gestes](../README.md#étapes-manuelles--m1-décomposer-et-suivre) distinguent le DELETE d’étape en 200 avec tâche complète du DELETE parent en 204. Le [composant d’étapes](../app/components/TaskSteps.vue) est hors du formulaire parent. Les mutations partagent la coordination tâches/catégories, `retry: 0` et le délai de 10 s. Une réponse incertaine bloque toutes les mutations jusqu’à relecture complète, sans effacer les brouillons. Le détail est identifié par le parent pour abandonner les brouillons à sa fermeture ou au changement de tâche.

[Tests SQLite](../tests/steps.test.ts) : migrations vierge/0000/0002, réapplication/réouverture, contraintes, transitions, rollback injecté par triggers et deux processus/connexions concurrents. [API](../tests/e2e/steps-api.spec.ts) et [parcours Playwright](../tests/e2e/steps.spec.ts) : protections, progression, séparation des brouillons, confirmations/focus, attentes et pertes de réponses. `pnpm check:persistence` et `pnpm check:recovery` exercent de vraies opérations HTTP d’étapes, puis comparent identifiants, titres, états et ordre après redémarrage ou restauration ; ils vérifient aussi la cascade sans orphelin. Tous utilisent des données jetables et exigent `pnpm build` à jour. Un viewport mobile ne valide pas le tactile ; le [checkpoint](../runs/current.md) précise les contrôles exécutés et la validation tactile M1 rapportée par l’utilisateur le 12 novembre 2026 sur A37 avec Chrome, sans OS ni versions précisés dans ce retour.
